# Schema documentation is generated, and its rationale lives in the schema

Status: accepted

## Decision

The database is documented in three layers, none of them hand-written prose about columns:

1. **Facts:** `docs/schema.sql`, generated by `dotnet ef dbcontext script` (`scripts/derive-db-docs.sh`). CI regenerates it with `--check` and fails on any change.
2. **Rationale:** PostgreSQL `COMMENT`s, set with `.HasComment(...)` next to the Fluent config they explain.
3. **Navigable view:** an ER diagram and table pages generated in CI by `tbls`, published as an artifact and never committed.

## Why

The hand-written schema description drifted badly (a missing table, wrong column names and case, columns that did not exist), and nothing could tell. The facts were never missing; they were *copied*. A generated Markdown renderer was tried and dropped: it was a third copy and a bespoke tool to maintain.

Rule: do not hand-build a layer a maintained tool covers, and do not restate a fact version control already holds.

## Consequences

- `docs/schema.sql` is never edited by hand.
- A comment change is a migration, not a text edit.
- EF has no `HasComment` for an index, so index rationale stays as code comments in `AnichronDbContext`.
- The check needs no database. The ER-diagram job does, so it is separate and cannot block a merge.
