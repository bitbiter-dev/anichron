# Ingestion

How the Worker crawls a storage config, classifies and reconciles each file, generates proxies, detects bursts, and owns failure.

## Worker Processing Model

Processing uses a bounded-concurrency `Channel<T>` pipeline. The crawler produces file paths; N consumer tasks process them concurrently. Default concurrency: `Worker:MaxConcurrentFiles = 4`. Processing is always idempotent — files already in the DB (matched by `(StorageConfigId, ContentHash)`) skip extraction and proxy generation; only the row's `FilePath`/`LastSeenOnNas` are updated, and a file whose bytes changed at a stored path updates that row in place (see Reconciliation below).

**Classify once, then one handler per outcome (#254).** Right after hashing, `ClassificationMiddleware` asks `IngestionClassifier`, which loads every relevant row in one query (`FindByHashesOrPathsAsync`: any row by either half's hash, any row at either half's path), and gives each half a `FileClassification`: a `FileOutcome` (`New`, `ContentChanged`, `Unchanged`, `Moved`, `DuplicateCopy`, `OverwrittenByCopy`, `OverwrittenByMove`, `AutoRestored`, `AutoRestoredMoved`, `AutoRestoredContentChanged`, `LoneLivePhotoVideo`; see Reconciliation below), `Stored` (the row the outcome acts on) and `Retired` (the row it soft-deletes), plus a `PairingAction` for the item (`None`, `AttachMov`, `PointAtMov`, `BackfillMovProxy`). No other step asks the database whether content is known, except `IngestionSaver` checking whether a concurrent consumer's row landed after a lost insert race. A `New`, `ContentChanged` or `AutoRestoredContentChanged` primary continues through EXIF, proxies and `PersistenceMiddleware`, which hands the write to the `IOutcomeWriter` whose `Outcomes` include it (`NewContentWriter` inserts, `ContentChangedWriter` updates the stored row in place; both share `ProcessedContentWriter`, whose `ContentOf` is the only EXIF → `AssetContent` mapping), after `KnownFileReconciler` has reconciled the MOV half. A stored row takes new content only through `StoredContent.TakeAsync` (content fields, `Metadata` through `MetadataValues.Copy`, proxy rows by type, burst mark cleared, reactivated), whether the content was processed (`ContentChanged`, `AutoRestoredContentChanged`) or comes from another row (`OverwrittenByMove`, `AssetContent.Of`); `StoredContent.ReactivateAsync` is the one place a row is auto-restored and its count staged (#327). Every other outcome stops the item after `LivePhotoPairer` and `KnownFileReconciler` have updated the stored rows. Each item stages on its context the rows it soft-deletes and auto-restores, `IngestionSaver` counts them once a save has persisted them (a lost save counts nothing), and the crawl sums them. Unique violations are recognised by index name with `IsUniqueViolation` (`Anichron.Core/Data/UniqueViolations.cs`). **Steps stage; the item's last step saves once, through `IngestionSaver.TrySaveItemAsync`, which reads the plan (#354).** The pairer, the reconciler and the writers only change tracked rows and register proxies, and none of them asks whether another step saves after it: `ClassificationMiddleware` saves a reconciled item when anything changed, and `PersistenceMiddleware` saves a processed one once its `IOutcomeWriter` has staged the row. An item therefore commits at most once and is atomic for every mix of outcomes; a failed item is redone whole on the next crawl. The plan is on the classification. When either half is `OverwrittenByMove`, the save soft-deletes every half's `Retired` row first, in one transaction (`IngestionClassification.RetiredFirst`). `PairingFor` says who writes a MOV's proxies: `AttachMov` (the pairer writes the missing ones) or `PointAtMov` (a MOV taking content, whose proxies the reconciler writes). `DatesMovAfterProcessing` says who dates a MOV taking content (below). A lost race returns false, and the item is skipped until the next crawl, for a processed row whose content another row committed or for an item that retires rows first; otherwise it rethrows. After a commit, and on a lost race, the save releases the proxies of every MOV whose proxies `PairedMovProxyWriter` registered (`IngestionContext.StageMovProxies`), because proxy paths are content-addressed and the winner's rows may point at them. Any other failure leaves them to compensation. A new outcome, as content changed at a known path (#250) was, is a classifier branch, a `FileOutcome` value and its handler or writer, and any write it adds goes into the item's one save. When a Live Photo's HEIC is already stored without its MOV (the halves arrived in different crawls), `LivePhotoPairer` attaches the MOV to the stored row, saved with the reconciled halves; `PairedMovResolver` reuses the MOV row the classifier left at the MOV's path rather than inserting a duplicate, and a MOV that copies another row's content is not paired at all. The paired MOV is its own asset and owns its `WebVideo` proxy, written into the MOV's own content-hash directory by `PairedMovProxyWriter` when the MOV takes new content, or else only when that MOV has none yet — on first ingest, on late pairing, and on any later crawl of an already-paired HEIC whose MOV still lacks it (self-heal).

## Worker Media Processing

- Crawls each storage config as its own `Crawl` work item (#281), due every `Worker:CrawlIntervalHours` (default 4 h) after the last one finished; the first crawl after a start comes from due-ness, so a restart that outlasted the interval crawls straight away. Progress is items found, processed and failed (a Live Photo pair is one item), with no total until the walk ends
- The crawl walks folder by folder and never enters `CrawlExclusions`: any dot-folder or dot-file (macOS/Linux/QNAP/ZFS/sync-tool metadata), NAS and OS system folders (`@eaDir`, `#recycle`, `@Recycle`, `$RECYCLE.BIN`, `lost+found`, Nextcloud `files_trashbin`/`files_versions`, …) and app library packages (`*.photoslibrary`, `*.lrdata`, …, which hold thumbnails and renders). `Worker:ExcludedDirectories` adds comma-separated folder names (not paths; rejected at startup) on top. An unreadable subfolder is logged and skipped; an unreadable or missing root fails that storage config's `Crawl` item with the error, and the other configs' items still run (#282)
- Computes XXHash64 `ContentHash` → extracts EXIF via MetadataExtractor → writes `MediaAsset` + `Metadata`
- Generates proxy types: `Thumbnail`, `FullPreview`, `WebVideo` (the `ProxyType` enum, persisted as text), and a BlurHash string for images, stored in `Metadata.Blurhash`
- Image proxies are auto-oriented once after decoding: upright pixels, orientation tag 1. `Metadata.Orientation` applies only when serving originals — never rotate a proxy by it
- Image proxy sizes are edge-based, so portrait and landscape get the same treatment: preview long edge `PreviewLongEdge` (1920), thumbnail short edge `ThumbnailShortEdge` (300), blurhash sample long edge `BlurhashSampleLongEdge` (64). Nothing is ever upscaled
- Each `IImageProxyGenerator`, and the `BlurhashEncoder`, declares a `ProxyBound`; `ImageProxyMiddleware` decodes once to `Rgb24`, shrinks the shared image to each bound largest-first, and hands every step **its own copy** at that size. The encoder's string goes on the `IngestionContext` and the content writer (`ProcessedContentWriter.ContentOf`) puts it in the content's `Metadata`. Generators may crop/recolour/resize their copy freely; only the middleware resizes the shared image
- FFmpeg transcodes video with runtime GPU detection: QuickSync (`h264_qsv`) → NVENC (`h264_nvenc`) → AMF (`h264_amf`) → software (`libx264`)
- Burst detection (#297, #298): a `BurstDetection` work item per storage config, enqueued by the config's `Crawl` when it finishes and scheduled at the crawl interval as a fallback (one dedup key, so never twice). `BurstDetectionHandler` reads and writes through `IBurstRepository` (Core). It first repairs the config's bursts (fewer than 2 active members: deleted; otherwise the earliest active member becomes the cover; bursts with no member rows, in any config, are deleted in one `ExecuteDelete` so concurrent Workers cannot conflict), then checks each unchecked photo (`Image` or `LivePhoto`, never `Video`, so a paired MOV never joins) oldest first, in batches: it reads the original once through `IOriginalPhotoReader` (EXIF capture time, Apple `BurstUUID`) and writes its `BurstCheck` row. A candidate (EXIF capture time, camera make and model, a thumbnail) joins every checked candidate of the config with the same `BurstUUID`, regardless of time. It is then compared with every checked candidate of the same camera make and model captured within `Worker:BurstGapSeconds` (120), except those its label already groups (a labelled frame or a member of its burst), through `IThumbnailMatcher` (each score logged at `Debug`, counted as matched or not), and joins each one scoring at least `Worker:BurstSimilarityThreshold` (0.25), oldest first, unless the joined burst's active members would span more than `Worker:BurstSpanSeconds` (300, at least the gap, checked at startup); camera-label joins ignore the span. Joins create or merge bursts (into the oldest, cover the earliest member); each photo saves with its burst changes, so checked pairs are never compared again. `OrbThumbnailMatcher` is the only OpenCV code (architecture rule `opencv-stays-in-the-matcher`, ADR 0009): ORB keypoints on the stored thumbnails, a ratio test and a RANSAC homography, the score being the share of keypoints that fit it; it describes each thumbnail once per batch. A missing root fails the item before anything is marked. Per-config handlers skip a missing or inactive config through `ActiveStorageConfigs`, returning `StorageConfigSkipped`.
- Reconciliation (#33, ADR 0011): classification reconciles every crawled file against the config's rows, top to bottom, first match wins: an active row with its hash at its path is `Unchanged` (`LastSeenOnNas` refreshed). With that row's file still on disk at another path Q, an active row at the crawled path P is soft-deleted (`OverwrittenByCopy`: `cp Q P`), otherwise the file is a `DuplicateCopy` (reported by #36). With Q gone, a row at P takes Q's content (`OverwrittenByMove`: `mv Q P`, **the path holder wins**): hash, capture date, media type, `Metadata` and proxy paths copied, not regenerated, burst mark cleared, `Id`, interactions and `PairedAssetId` kept; Q's row is soft-deleted first and P's row saved second, in one transaction (`IngestionSaver.TrySaveItemAsync`), and a soft-deleted P is auto-restored. With no row at P, Q's row moves (`Moved`, #35). With no active row holding the hash, an active row at P was **edited in place** (`ContentChanged`, #250): processed like new content, and `ContentChangedWriter` updates that row (new hash, capture date, media type, `Metadata`, proxy rows by type; `Id`, interactions and `PairedAssetId` kept; burst mark cleared). A soft-deleted row at P is **auto-restored**: as it was (`AutoRestored`, proxies and `Metadata` reused) or with its content changed (`AutoRestoredContentChanged`, through `ContentChangedWriter`). Otherwise the most recently seen soft-deleted row with the hash is auto-restored at P (`AutoRestoredMoved`), else the file is `New`. Ahead of all of this, **a video crawled alone whose matched rows include a Live Photo's video** (a row some photo, active or soft-deleted, points at through `PairedAssetId`: `MatchedAsset.IsLivePhotoVideo`, an `EXISTS` in the same query) is a `LoneLivePhotoVideo` (#321): that row is never refreshed, moved, restored or retired, since it follows only its photo; an active row at P that is not one is soft-deleted, as a copy of the video over it; the path counts as found. The same holds for a Live Photo's MOV half that has no paired row to be classified against (below) when the matched Live Photo's video is not the item's own (as after `cp B.heic A.heic`), and its pairing is then `None`, so it is never restored only for the sweep to retire it again. Auto-restore clears `IsSoftDeleted`, refreshes `LastSeenOnNas` and deletes the `BurstCheck` row; interactions are untouched, so a hidden asset stays hidden. After ingestion, `MissingFileSweep` soft-deletes, with one `ExecuteUpdate` per batch, the config's active rows whose path the walk did not find (both Live Photo halves of a queued item and failed items count as found; excluded folders do not), plus every active video that a missing photo points at, found or not, so a Live Photo goes as one (#321), unless the walk skipped an unreadable folder (`IncompleteWalk`) or found no media while the config has active rows (`EmptyRoot`). The crawl's `Result` carries `reconciliation { softDeleted, autoRestored, skippedBecause }`, logged in one `Information` line; counts are rows, so a Live Photo counts 2. Each soft-deleted path is logged at `Debug`, a soft-delete at classification at `Information`, and so is a Live Photo's video soft-deleted (missing) or auto-restored beside an active photo, which makes the photo a still photo or a Live Photo again. **A Live Photo is reconciled as one unit (#331).** The photo is classified first; its row is the one its outcome leaves at its path (`FileClassification.Row`: none for `New`, `DuplicateCopy` and `OverwrittenByCopy`, whose `Stored` is the other copy). When that row's `PairedAssetId` row is among the results, the MOV half runs the same table with that row as the row at its path, unless another row, active or soft-deleted, holds the MOV's path: **the path holder wins** and the photo is re-pointed to it. The paired row follows the MOV's path (`Moved`, not `Unchanged`, when it holds the hash elsewhere). Otherwise (no photo row, a photo never paired, or a paired row missing from the results, as when a whole Live Photo is moved and its video edited at once) the MOV is looked up by its own hash and path, and `AttachMov` inserts or attaches it. An edited MOV (`ContentChanged`, `AutoRestoredContentChanged`) has its `WebVideo` written into the new hash's folder by `PairedMovProxyWriter.WriteForNewContentAsync` and takes the content through `StoredContent.TakeAsync` (`Video`, empty `Metadata`, and the photo row's capture date, or the MOV's last-write time when there is no photo row). When the photo is processed too (`IngestionClassification.DatesMovAfterProcessing`), the MOV takes its content undated, whether edited or `OverwrittenByMove`, and `ProcessedContentWriter` dates it once, from the processed photo's date; `BackfillMovProxy` never runs for a MOV taking content. Interactions stay on the photo row. **A video has one photo, and a soft-deleted photo never points at an active video (#350).** Each rule has one home. Pairing goes through `PairedMovResolver.PairAsync` (used by `LivePhotoPairer` and `ProcessedContentWriter`): when the video row is stored, every other photo whose `PairedAssetId` is still that video lets go of it (an active one is logged at `Information` as now a still photo), as when `mv B.heic A.heic; mv B.mov A.mov` onto a still photo A hands B's video to A before B is retired; a unique index on `PairedAssetId` makes any other path fail the save. Retiring at classification goes through `StoredContent.RetireAsync` (`OverwrittenByCopy`, `OverwrittenByMove`'s moved row, a row a `LoneLivePhotoVideo` overwrites): it soft-deletes the row and, when it has a `PairedAssetId`, the video too (the tracked row, else loaded by id), each counted once, in the item's one save; a row already soft-deleted is left alone, so a video its photo took along is not counted again by its own MOV half. No exception is needed, since a retired row with a `PairedAssetId` is always a photo retired after pairing: without processing, the pairer runs before the reconciler; with processing, the MOV half is reconciled first, but it retires only rows at the MOV path, and pairing never sets a video's `PairedAssetId`. A MOV half is reconciled before its HEIC is processed. A move onto a path a concurrent consumer took after classification fails the save, and the item is retried on the next crawl; two rows taking one hash at once lose as a `LostIngestionRace`, skipped until the next crawl. Swapping two paths' contents can soft-delete both rows for one crawl; the next auto-restores them
- Duplicate content is **reported, never merged** (#36). `SharedContentReporter` runs at the end of each config's `Crawl` item: it logs one `Information` summary for the crawled config (copies within it, counted by that crawl from each item it ingested, and pairs of its active rows sharing a `ContentHash` with the same user's other active configs), with each pair at `Debug`, and the counts go into the crawl's result. A pair across two configs is reported by each of their crawls. A failed report is logged and does not fail the crawl. Duplicates across different users are expected and never reported. Two new identical copies racing in one crawl are first reported on the next crawl
- Failure ownership: `ProxyStagingWriter` is the single place a proxy reaches its final name (architecture rule `proxies-reach-final-name-only-in-staging-writer`) — it writes under a per-attempt `.<attempt id>.tmp` suffix (so concurrent attempts on the same content never share a temporary file), renames into place once complete, and registers the proxy on the `IngestionContext` at that moment; the proxy middlewares only supply the bytes. If a step throws, `IngestionPipelineRunner` deletes the registered proxies this attempt **created** (never a final file that existed before the attempt, since a proxy path derives from content and another row, active or soft-deleted, may reference it) plus its own temporary files, and removes the directory only if it is left empty — never recursively, since a concurrent attempt on the same content shares it until one of them persists. An attempt that loses a uniqueness race (`LostIngestionRace`: the active content-hash index or the one-proxy-per-asset-and-type index) first releases the registrations of every MOV the item staged, because the winner owns those content-derived files. A clean shutdown is treated differently: the in-flight temporary file is dropped, but proxies already completed in that run are kept, and the consumer loop re-throws the cancellation instead of recording an item failure and draining the queue. Each attempt has its own `IngestionContext.AttemptId`, which names temporary files and scopes compensation; `IngestionContext.AssetId` is the row that owns the proxies, set by classification (the stored row for `ContentChanged`, the attempt id for new content). A hard kill, the storage-config cascade delete, and the old content directory of a file edited in place are out of reach in-process and are reclaimed by an admin through a proxy sweep (`work-queue.md`, "Proxy sweeps"); the old directory is deliberately not deleted after commit, because a copy of the old content elsewhere can be ingested into it in the same crawl.
